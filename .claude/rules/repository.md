# Repository Management Rules

- The current user request has highest authority. For Git commit timing, message format, branch rules, and required checks, use applicable company/project instructions discovered under `input/` before the framework defaults in `repository-manager.md`. Cite the source path and section. Do not copy a stale policy summary into every task.
- Before a bug fix, new feature, refactor, documentation/Artifact amendment, or other mutation, identify a committed baseline and inspect repository status. If planned write paths contain uncommitted changes, commit authorized work under the applicable policy or isolate it before dispatch; never silently include unrelated user files.
- An applicable company policy may defer an intermediate commit. Cite and pin its exact `input/` section in the handoff, declare `defer_commit` and `commit_policy_path`, and take a verified snapshot of the dirty write scope before continuing. The script checks the cited bytes and snapshot; the Orchestrator must verify the policy's meaning.
- Preserve predecessor bytes in a verified scoped Git snapshot before amendment, and preserve the reviewed revision before review. The executable handoff guard must verify the snapshot ref and selected content before dispatch.
- At task start, Agent return, review/Gate boundary, commit, resume, and stop, record or inspect branch, HEAD, staged/unstaged/untracked paths, active handoffs, and relevant snapshot refs. Use concise evidence rather than continuous polling.
- The `repository-manager` owns scoped commits and repository-state reporting in STANDARD/STRICT work. The Orchestrator still owns Stage/Gate decisions and may run cheap read-only status checks. A company policy that specifies a different commit moment overrides the default timing, while the required recovery snapshot remains separate.
- A repository-manager handoff must distinguish status work from a commit action. For a commit, declare exact `commit_paths`; successful `finish` requires a new, scoped, clean commit and validates the default subject unless a pinned `input/` policy overrides it. Keep each active worktree to one task; use separate worktrees for independent parallel work, and let `finish` compare actual changed files with declared outputs and recoverable predecessor snapshots.
- No empty baseline commits when HEAD already represents a clean workspace. Never reset, clean, amend reviewed commits, force-push, or commit secrets to simulate compliance.

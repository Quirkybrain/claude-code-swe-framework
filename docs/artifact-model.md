# Artifact Model

## Purpose

Artifacts are durable, reviewable outputs that connect software-engineering work. They are the primary interfaces between the main Orchestrator, specialist Agents, lifecycle stages, and resumed sessions.

An Artifact may be supplied by the user, discovered in an existing project, or generated by the Framework. Existing files are not automatically valid Artifacts; their type, state, provenance, and target fitness must first be established.

## Core Record

Every managed Artifact must expose or register the following fields.

| Field | Meaning |
|---|---|
| **Artifact ID** | Stable unique identifier, such as `REQ-001`, `ADR-003`, or `TEST-052` |
| **Artifact Type** | Semantic type based on content, such as Requirement, Architecture, API Contract, Code, or Test Report |
| **Producer** | Generating entity: `agent:<agent-name>` or `orchestrator:main-session \| Deviation: <reason>`. Required for process compliance |
| **Status** | Current lifecycle status from the canonical Artifact states |
| **Source** | Original asset paths, user decisions, code locations, or upstream evidence from which it was derived |
| **Owner** | Role or Agent responsible for the current revision; ownership does not grant final approval |
| **Upstream Dependencies** | Artifacts and versions required to create or validate this Artifact |
| **Downstream Dependencies** | Known Artifacts that consume this Artifact and may become stale when it changes |
| **Validation** | Checks performed, evidence, result, validator, scope, and date/version evaluated |
| **Assumptions** | Material inferences that remain true for this revision |
| **Decisions** | User, product, architecture, or engineering decisions embodied by the Artifact |
| **Traceability** | Links to requirements, designs, Components, tasks, tests, findings, or release evidence |
| **Revision** | Monotonic revision label or repository version reference |
| **Last Verified** | Last time/revision at which the Artifact passed validation for its stated purpose |

Recommended supplemental fields:

- Title and summary
- Lifecycle stage
- Target relevance
- Open issues and known limitations
- Supersedes / superseded by
- Confidentiality or handling notes
- Definition of Done

## Canonical States

| State | Definition | May directly satisfy a downstream dependency? |
|---|---|---|
| `MISSING` | The required Artifact does not exist or cannot be located | No |
| `PARTIAL` | It exists but required content or coverage is incomplete | Only when the consumer explicitly accepts the documented gap |
| `UNVERIFIED` | It exists, but its correctness, freshness, consistency, or fitness has not been established | No; validate first |
| `VALID` | It passed appropriate validation and is sufficient for the current target and declared scope | Yes |
| `STALE` | A relevant upstream dependency changed after validation | No; revalidate or revise |
| `INVALID` | Evidence confirms it is incorrect, contradictory, obsolete beyond reuse, or unsuitable for the target | No |

`VALID` is always relative to a revision, validation scope, dependencies, and target. It is not permanent.

## State Transitions

Typical transitions:

```text
MISSING → PARTIAL → UNVERIFIED → VALID
               ↘           ↘       ↓
                INVALID ←───┘     STALE
                                  ↓
                       UNVERIFIED / VALID / INVALID
```

Rules:

1. A newly discovered user asset normally starts as `UNVERIFIED` or `PARTIAL`, not `VALID`.
2. A generated Artifact is `UNVERIFIED` until required checks pass.
3. A relevant upstream revision changes a previously `VALID` downstream Artifact to `STALE`.
4. Editing a `VALID` Artifact creates a new revision that must be validated again.
5. Validation may move `UNVERIFIED` or `STALE` to `VALID`, `PARTIAL`, or `INVALID`.
6. `MISSING` may be represented in the registry even though there is no corresponding file.
7. Historical evidence is retained when practical but must not be presented as current evidence.

## Artifact Type Is Content-Based

Directory, filename, and extension are classification hints only. An image may represent UI, architecture, process, or deployment. A Markdown file may contain requirements, an ADR, a test report, or unrelated notes.

Project Intake must inspect accessible content and record the basis of classification. If content cannot be interpreted reliably, the classification and claims remain `UNVERIFIED`.

## Dependency Model

Each Artifact type may define:

```text
Requires:
- minimum upstream Artifacts needed to produce or validate it

Can Reuse:
- existing assets or alternative evidence that may satisfy part of the need

Produces / Enables:
- downstream Artifacts or decisions this Artifact can support

Validation Rule:
- checks and evidence needed for VALID
```

The dependency graph connects Artifacts, not Agents. Agents can be replaced or combined without changing the engineering dependency.

Dependencies should identify the consumed revision where possible. This lets Change Impact Analysis distinguish affected work from unrelated work.

## Reuse Before Regenerate

Before replacing an existing Artifact, evaluate:

- completeness for the current target;
- internal consistency;
- consistency with other authoritative Artifacts;
- correctness supported by evidence;
- freshness relative to dependencies;
- fitness for intended downstream consumers.

Choose and record exactly one disposition:

| Disposition | Use when |
|---|---|
| Reuse | Existing Artifact is valid and sufficient |
| Supplement | Useful content exists but has bounded gaps |
| Revalidate | It may still be correct, but evidence is missing or stale |
| Regenerate | It is invalid or supplementation would cost more and carry more risk |

## Validation Record

A validation entry should include:

```text
Artifact ID and revision:
Validation scope:
Input dependency revisions:
Checks performed:
Evidence paths:
Result:
Validator:
Date / repository revision:
Known limitations:
```

A result without evidence or declared scope cannot establish `VALID`.

## Assumptions and Decisions

Assumptions are inferred facts used to proceed. Record their rationale, risk, affected Artifacts, and how they can be confirmed. A disproven assumption triggers Change Impact Analysis.

Decisions are explicit choices. Material architecture or technology choices should use an ADR with Context, Decision, Consequences, and considered alternatives. User answers must be persisted in a suitable Requirement, Constraint, Decision, or ADR rather than left only in chat.

## Traceability

Traceability should support both directions:

```text
REQ-001 → USECASE-003 → DOMAIN-002 → API-007
        → COMPONENT-012 → TASK-031 → TEST-052
```

It must be possible to determine:

- whether a Requirement is implemented;
- where it is implemented;
- which tests verify it;
- why code without a Requirement exists;
- what becomes affected when an upstream Artifact changes.

Traceability depth follows Process Budget. Lightweight tasks may use a compact change-to-test link; Strict work may require a formal matrix.

## Artifact Handoff

A handoff identifies the target Artifact, input paths and revisions, Project Constraints, assumptions, allowed write scope, Definition of Done, Gate, output location, and required validation evidence.

Chat summaries may accompany a handoff, but they do not replace the persisted Artifact or its registry entry.

## Generate on Demand

Create an Artifact only when it reduces relevant risk, enables downstream work, improves collaboration or maintenance, supports the current target, or is explicitly requested. The existence of a template does not make an Artifact mandatory.
